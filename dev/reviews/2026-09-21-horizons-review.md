## r-craft

Baseline used: `R/utils-errors.R`, `R/class-core.R`, `R/pipeline-average.R`, `R/pipeline-standardize.R`.

### Important

- **`R/pipeline-select-training.R:655`** — In `report_selection()`, the `scope == "global"` branch uses `ps$available` where every other reference in the loop is indexed (`ps$property[i]`, `ps$drawn[i]`, `ps$available[i]`). With more than one property `paste0()` vectorizes and `cat()` emits the whole vector on one line, so the global report is garbled exactly when it carries the most information. Fix: `ps$available[i]`. (Untested — the only `scope = "global"` verbose path in the suite is single-property.)

- **`R/pipeline-select-training.R:613`** — `check_resemblance()` calls `sample.int(n, 2000L)` with no seed and no RNG restoration. Two consequences: the "targets beyond the pool's spread" warning is non-reproducible for any pool over 2,000 rows (i.e. every real KSSL run), and the call silently advances the caller's `.Random.seed`. `cluster_targets()` (`R/select-neighbours.R:325-330`) goes to real trouble to restore RNG state; this path does not. Violates `r-work.md` "set seeds where stochastic behavior matters" / "avoid hidden state". Fix: thread `select_training()`'s `seed` through, wrap in the same save/restore, and widen the `@param seed` doc, which currently says "Seed for the clustering" only.

- **`R/select-neighbours.R:239-247`** — Silently short draw. `nearest_neighbours()` is asked for `min(kp + 1L, length(measured))`; when `length(measured) == kp` the spare neighbour does not exist, so dropping a twin leaves `kp - 1` rows for that target with no record anywhere — `membership` simply has one fewer row, and `pool_sizes` reports the union, not the per-target count. The package's own posture (`safely_execute()`, `create_failed_result()`, `r-work.md` "record failures, don't swallow") is that degradation is recorded. Either record a per-target shortfall in the selection record or require `length(measured) > kp` when twins are possible.

- **`R/select-neighbours.R:339, 360, 369`** — Local variable named `assign`, shadowing `base::assign`, inside a function whose `on.exit()` handler (line 328) calls `assign(".Random.seed", ...)`. It only works because R skips non-function bindings when resolving a call. That is a coincidence, not a design. Rename to `labels` or `cluster_of`.

- **`R/pipeline-select-training.R:162-248`** — Formatting drift in the validation block. The package writes a blank line after every opening brace, including one-statement bodies: `pipeline-average.R:102-107` is the *same* validation idiom, fully spaced, as is the error-reporting `for` at `pipeline-average.R:148-153`. The new block compresses all of them (`162-164`, `166-168`, `187-189`, `191-193`, `213-215`, `223-225`, `229-231`, and the `for` at `239-242`). Same drift in the inline lambdas at `290-295` and `304-308`. This is the one dominant style divergence in the branch.

- **`R/pipeline-select-training.R:219`** — `if (k_ok && length(k) > 1L || (k_ok && !is.null(names(k))))` mixes `&&` and `||` unparenthesized and repeats `k_ok` in both arms. It happens to be correct under R's precedence, but a reader has to verify that. Write `if (k_ok && (length(k) > 1L || !is.null(names(k))))`.

- **`R/pipeline-select-training.R:391`** — `cli::cli_inform()` for the cluster-fallback status bypasses the verb's own console layer. Everything else in `select_training()` is gated on `verbose` and rendered through the `cat`/box-drawing tree; this one line prints regardless, so `select_training(..., scope = "cluster", verbose = FALSE)` is not silent. The `verbose = FALSE prints nothing` test passes only because it uses `scope = "batch"`. Route it through the tree, or gate it on `verbose`.

### Suggestions

- **`R/select-neighbours.R:233-264`** — `draw_neighbours()` builds one 2-column tibble per target per property inside a double loop, plus `tid %in% twins$target_id` and `twins$pool_id[twins$target_id == tid]` linear scans per iteration. At the intended scale (thousands of targets, `k = 400`) that is tens of thousands of tibble constructions and an O(targets × twins) scan. The ids/dist matrices from `nearest_neighbours()` are already rectangular — one `tibble()` per property from the flattened matrices, with the twin drop applied via a `match()` lookup, is both faster and shorter.

- **`R/select-neighbours.R:97`** — `order(D[j, ])[seq_len(k)]` fully sorts a pool-length vector per target when only the k smallest are wanted. `order(D[j, ], method = "radix")` or a partial selection is a cheap win on the dominant inner loop.

- **`R/select-neighbours.R:379-380`** — `sapply()` (only 4 uses package-wide, against many `vapply`) followed by a defensive `matrix(cent, ncol = ...)` reshape to undo `sapply`'s type instability. `vapply(others, ..., numeric(ncol(St)))` gives the matrix directly and drops the reshape.

- **`R/select-neighbours.R:318-319`** — The `one <- function(reason) list(...)` continuation is indented one column past its opening paren and its list `=` are not aligned, against the alignment convention held everywhere else in the branch (e.g. `R/utils-subset.R:1971-1976`).

- **`R/select-neighbours.R:392`** — `sprintf()` for a user-facing reason string; the file otherwise builds message text with `paste0()`/`cli`.

- **`R/pipeline-select-training.R:250-254` vs `R/select-neighbours.R:186-204`** — The per-property `k` resolution rule is implemented twice, with the "A named `k` needs an entry for every property" message duplicated verbatim. One `resolve_k(k, properties)` helper would keep the two from drifting.

- **`R/pipeline-average.R:349-356`** — The `by`→`sample_id` rename is unguarded. The comment argues the original `sample_id` was not carried into `averaged`, but nothing asserts it; if that ever stops holding, the rename produces duplicate column names rather than an error. Also, a numeric `by` column yields a numeric `sample_id`, and `validate_horizons_data()` checks presence and uniqueness but not type (`R/class-core.R:308-322`), so it would pass and then surface later in `subset_rows()`, which dispatches on `is.character(keep)`. A `stopifnot()` plus `as.character()` costs two lines.

- **`R/utils-recipes.R:85`** (worktree) — The comment names `select_training()`'s three provenance columns, but the change relaxes the bake requirement for *every* meta column in every recipe the package builds. The code is broader than its justification. Either widen the comment to say so explicitly, or scope the relaxation to the provenance columns. Whether the wider behavior is correct is recipe-steps/leakage territory; the comment-vs-code mismatch is the craft issue.

### Consistency notes

Following the package well: the red-tree validation-accumulate-then-`rlang::abort` block matches `pipeline-average.R`/`pipeline-standardize.R` including the error class choice; `cli::cli_abort(..., class = "horizons_input_error")` throughout the internals rather than bare `stop()`; no `library()`/`require()`, and non-base calls are namespaced consistently (including `stats::`, `utils::`); `## ----` section headers at the right hierarchy; `=` alignment in signatures and named lists; `@noRd` on every internal with `@seealso` cross-links; new deps (`cluster` in Imports, `mixOmics` behind `rlang::check_installed()` in Suggests) declared correctly. The tests are notably strong craft: brute-force reference implementations for the distance metrics and an inline transcription of the experiment's chain as the space's oracle, plus Arrange/Act/Assert comments matching the existing suite.

Two things worth calling out as genuinely good design rather than just conformance: `cluster_targets()`'s RNG save/restore, and `set_analysis()`/`subset_rows()` collapsing the derived-count invariant to one place, with `validate()` and `average()` converted onto it.

The single drift worth fixing package-wide before it compounds: blank lines inside braces in the new validation and lambda bodies.

## leakage-lifecycle

Everything below was checked against the source, and the three Critical findings were reproduced against the package's own fixture (`make_select_fixture()`), not inferred from the diff.

### Critical (silent metric inflation / void guarantee)

- **`R/select-neighbours.R:136` (+ `:241`) — the twin rule fails on exactly the case it was built for: a pool that contains replicate scans.** `is_twin <- d1 == 0 | d1 < ratio * d2` compares the nearest distance to the *second* nearest. When a target has two near-copies in the pool, both distances are tiny, the ratio is ≈ 1, and nothing is flagged. Reproduced: two replicate scans of a target's pool row (σ = 5e-4 on absorbance) → `exclusions` has **0 rows**, both self-rows sit in that target's own neighbourhood at distances 0.0119 and 0.0150 against a third-nearest of 2.28, and both are in the returned training set. The exact-plus-replicate case is only half-caught: the bit-exact row is excluded, the replicate survives, because `:241` drops a single id (`twins$pool_id[...][1]`) and `:228` fetches only one spare neighbour. Information path: the target's own lab value enters the training set, the model predicts that target from its own reference measurement, and every downstream batch RMSE/bias for affected targets is understated without bound. Silent twice over: the record reports zero exclusions and the verbose tree prints "Twins excluded: 0". Fix: the rule shape has to change, not just the constant — judge each of the k distances against the neighbourhood's own spread (e.g. `d_j < ratio * median(d)` or against the k-th distance), drop every row that qualifies, and fetch enough spares to still reach k. The KSSL-replicate calibration the spec defers can then set the constant on a rule that works.

- **`R/pipeline-select-training.R:403` — the twin exclusion is per-neighbourhood, but the return is the union, so an excluded twin walks back in through any other target that drew it.** Reproduced at `k = 40` on the fixture: `P025` is excluded from `T01`'s neighbourhood and recorded in `exclusions`, is drawn by `T02` and `T04`, and is in `out$data$analysis`. At the default `k = 400` over a coherent batch of a hundred targets — where every target's neighbourhood overlaps its neighbours' heavily — this is the normal case, not the corner case. Under `scope = "batch"` (the default and the load-bearing one) the per-target exclusion buys essentially nothing. Silent because the record states the twin was excluded and it is true of the membership table and false of the training set. Fix: for `batch`/`cluster`, subtract the excluded pool ids from the union (or at least from the group holding the twinned target) and report the count separately from the per-neighbourhood exclusions.

- **`R/utils-recipes.R:30-35` — a second lab-measured response silently becomes a model predictor.** The verb's return contract keeps *every* pool response even when `properties` names one (`R/pipeline-select-training.R:437`, asserted by the test at `test-pipeline-select-training.R:263`). `configure(outcome = "clay")` leaves `oc` at role `response`; `build_recipe()` builds `outcome ~ .` and re-roles only `id`, `meta` and `covariate`, so `role == "response"` falls through to predictor. Verified with `summary(build_recipe(...))`: `oc` role = **predictor**, 427 predictors for 426 wavenumbers, and it is inside `all_predictors()` in every feature-selection branch (`utils-recipes.R:148-172`). Information path: a lab measurement of the same physical sample, correlated with the outcome in any real library, trains the model and is scored by the pool-internal CV — inflated CV and test metrics that cannot transfer, since the column can never exist for targets. Two layers of silence: `evaluate()` returned `status = "success"` on my run even with 86 of 174 rows carrying `NA` for `oc`, and `models$predictor_schema` records only the 426 wavenumbers, so `predict()`'s schema gate passes. It surfaces only at bake, as `The required column "oc" is missing`. **This is why the uncommitted regression test does not pass** — `NOT_CRAN=true testthat::test_file(...)` fails at `test-pipeline-select-training.R:277` with exactly that error. The `bake = FALSE` change in the worktree is correct and necessary, but it is not the blocker. Fix: `build_recipe()` should `step_rm()` every `role == "response"` column that is not the outcome (the invariant belongs there, shared seam with recipe-steps); narrowing the verb's return to `properties` would also help but would not close the hole for `add_response(variable = c(...))`.

### Important

- **`R/pipeline-select-training.R:334-348` — `scope = "global"` skips the twin check entirely, and the record and report assert zero twins.** The global branch computes distances for `target_distances` only and hands back an empty `exclusions` tibble. The verb's stated job is to be the instrument for the batch-versus-global comparison; whenever the targets are in the library, the control arm is leaked and the selection arm is not, which biases the comparison in a fixed direction. Fix: run `find_twins()` under `global` too and report it, even if the rows stay.

- **No pool-internal de-duplication, and the resampling downstream is ungrouped.** `pipeline-evaluate.R:220/247` use plain `initial_split()`/`vfold_cv()`. Replicate scans of one library sample are each other's nearest neighbours, so a target that draws one draws all of them: the selected training set is *enriched* in sibling pairs relative to the pool it came from, and tighter k enriches it further. Plain CV puts siblings on both sides of every fold. Effect scales inversely with k, which biases the k sweep that is test 1 on the design's own list. Fix: dedupe the union on near-zero similarity-space distance before returning (reported like twins), or carry a sibling group id in the record so `evaluate()` can use `group_vfold_cv()`.

- **`R/select-space.R` (PLS branch) — `space = "pls"` selects rows using those rows' own responses.** No target leakage (targets are unlabeled, so the batch prediction stays honest), but which pool rows land in the training set *and* in `evaluate()`'s held-out `test_F` was decided by a space fit on their y. That is selection-on-outcome upstream of the split, and no fold structure undoes it; the pool-internal estimate is optimistic and nothing warns. Fix: note it on the record and in print, and score PLS-space runs against the targets rather than the pool CV.

- **Conformal calibration and the AD bundle after selection.** `fit()`'s calibration set is drawn from the selected pool — rows chosen precisely for being near the targets. Coverage holds under exchangeability between calibration and prediction data, which selection deliberately breaks (the off-library batch is the whole motivation). `predict(interval = TRUE)` on targets therefore carries no coverage guarantee and says nothing. The record already holds `target_distances`, which is the right signal. Fix: document, and warn when interval prediction runs on a fit whose training object carried `$selection`.

- **The selection record is not maintained when rows leave.** `validate(remove_outliers = TRUE)` now routes through `subset_rows()` (`pipeline-validate.R:441`), but `$selection$membership`, `$groups$pool_ids`, `$pool_sizes` and the `.drawn_by` counts still describe the pre-removal set. This fires on the default path — my fixture run dropped 5 spectral outliers. For `cluster`/`sample` the downstream loop reads `groups$pool_ids`, so it either aborts on ids the object no longer has or fits a group quietly smaller than the record claims. Fix: recompute or explicitly invalidate the record when rows change.

- **`R/utils-subset.R:60-70` — `set_analysis()` recomputes counts but leaves downstream state alone.** `x$data$split`, `$data$row_index`, `$evaluation` and `$models` survive a row change with stale `.row` indices. Not reachable today (both call sites run pre-split), but the docstring invites exactly the later use — "a per-group fit, a holdout" — that would make it reachable. Fix: abort, or clear loudly, when a split or evaluation exists.

### Suggestions

- `R/pipeline-select-training.R:613` — `sample.int(n, 2000L)` is unseeded, so for any pool over 2,000 rows the resemblance threshold, the "beyond the pool's spread" warning and the stored record differ between identical calls, and the call perturbs the caller's RNG stream. `cluster_targets()` (`select-neighbours.R:310-315`) does the save/restore correctly; mirror it, or take a deterministic stride instead of a sample.
- No label-permutation test on the selection path. Permute the pool's responses, rerun `select_training() |> configure() |> evaluate()`, assert the pool CV collapses. It is the single highest-leverage detector here, and under `space = "pls"` it also exercises the PLS finding above, because the selection itself becomes outcome-driven noise.
- No assertion that the meta provenance columns never become predictors. They currently do not (verified at the recipe level), but `.min_distance` is a direct function of target proximity and would be undetectable if promoted. Assert on `summary(build_recipe(...))$role`, not just on the role map.
- Add a twin fixture with two replicate pool rows. The suite's only twin case is a single exact copy — the one configuration the gap rule handles.

### Validity verified

- The return carries the pool's original standardized spectra resampled onto the targets' grid, never the similarity-space transform: `rebuild_predictors()` is fed `rc$matrix`, and the tests assert the output wavenumbers equal the target grid and `n_predictors == length(target_wn)`.
- Reconciliation is per-spectrum spline interpolation (`resample_spectra(new_wav = )`), a row-wise operation with no cross-sample statistic — leakage-safe wherever it runs. Only the axis crosses from targets to training data, not values.
- The PCA space is unsupervised, and no score column leaves the verb.
- The twin check is correctly scoped per property and per target: `draw_neighbours()` loops properties, restricts candidates to rows with that property measured, and runs `find_twins()` within that candidate set — the ranking and the second-nearest reference are both property-local. The defect is in the rule, not the scoping.
- The per-property draw genuinely restricts to measured rows, so a sparse property is reported honestly rather than thinned.
- Meta-role columns are not predictors, and the worktree's `bake = FALSE` is the right call: `id` keeps `bake = TRUE` and `resolve_new_data()` supplies `sample_id`, so nothing downstream needs a meta column at bake time.
- `space_rows = "measured"` fits, projects and scales consistently per property, each draw using its own space's `sdev`.

## s3-contract

### Critical (broken invariant or silent corruption)

- **`R/pipeline-select-training.R:162,405,458`** — `select_training()` builds its return by subsetting the *pool* object (`subset_rows(pool_rc, union_ids)`) and never clears anything the pool was carrying. It only ever writes `out$data` and `out$selection` (grep of `out$` confirms: lines 436, 437, 458, 487). So if `pool` is anything other than a freshly loaded `horizons_data`, the returned training set inherits, unmodified: `config$configs` / `n_configs`, `validation$passed`, `validation$checks`, `validation$outliers$*_ids`, `evaluation$results` + `evaluation$split`, `models$*` (including `row_index` and `predictor_schema`), and — because `subset_rows()` preserves `class(x)` — the pool's **class vector**. The entry guard at line 162/166 is `inherits(pool, "horizons_data")`, which is `TRUE` for a `horizons_eval`/`horizons_fit`/`horizons_ensemble`.

  Broken: promotion is supposed to be additive and *earned* (01-object-contract.md, class semantics + I5/I6). Here a `horizons_fit` comes out the other side of a row-selection verb still claiming `horizons_fit`, with `models$row_index` and `evaluation$split` keyed to `.row` positions of the *pool's* row order, which the subset just destroyed. Downstream: `predict()` runs off `models$workflows` trained on rows that are no longer in `data$analysis`; any join-back through `row_index` maps `.row` to the wrong `sample_id` (the "right numbers, wrong soil" failure). The milder and far more likely case is the same shape: a pool that was merely `validate()`d returns with `validation$passed = TRUE` and `outliers$removed_ids` naming rows that were never drawn, so `summary()`'s pipeline-status logic (`class-core.R:2279`) reports the next step as `evaluate()` and skips `validate()` on a table it has never seen. Nothing catches this — `validate_horizons_data()` at line 494 only inspects `data`.

  Fix: require `identical(class(pool), c("horizons_data", "list"))` (or explicitly reset `config`/`validation`/`evaluation`/`models`/`ensemble` and the class vector) before building the return. `configure()` already has the precedent for clearing stale downstream state (`pipeline-configure.R:300–318`).

### Important

- **`R/utils-subset.R:37,107`** — `set_analysis()` and `subset_rows()` both guard with `inherits(x, "horizons_data")`, which admits every promoted class. They then replace `data$analysis` and recompute counts while leaving `models$split`, `models$row_index`, `models$predictor_schema`, `evaluation$split` and `validation$*` untouched. These are the two primitives everything else now routes through, so this is the root of the critical above. Either restrict them to an unpromoted `horizons_data`, or make them explicitly reset the dependent slots and say so in the docs. As written, the doc claim "everything outside `x$data` is unchanged" is exactly the problem, not the guarantee.

- **`R/pipeline-select-training.R:416,424`** — `.min_distance` is computed as `min(d$distance)` over `membership` rows for a pool id, pooled across properties. Under `space_rows = "measured"` (lines 503–512) each property gets its **own** PCA/PLS space with its own `sdev`, so the distances in `membership` are in different, incommensurable units per property. Taking a `min` across them yields a number with no defined scale, and `.group` (line 424–433) picks "the nearest drawing target" by the same cross-space comparison, so the group label a row gets can be decided by which property happened to have the smaller-scaled space. `selection$target_distances` is fine because it carries a `property` column; the two meta columns are not. Either carry `.min_distance`/`.group` per property, or restrict them to the single-space case and write `NA` under `space_rows = "measured"` with >1 property.

- **`R/class-core.R:370`** — the wavelength-order check is dead code. `numeric_predictors <- predictor_vars[grepl("^[0-9.]+$", predictor_vars)]` never matches, because every predictor column in the package is named `wn_<wavenumber>` (`pipeline-spectra.R:636,1008`, `pipeline-standardize.R:709`, and now `pipeline-select-training.R:536`). `length(numeric_predictors) > 1` is therefore always `FALSE` and invariant I2's "strictly decreasing" requirement is never enforced on any object. The print and summary methods already use the right pattern (`^(wn_)?[0-9.]+$`, lines 1587 and 1895), so the validator is the odd one out. This is pre-existing, but it matters more now: `rebuild_predictors()` is a second place that mints predictor names from a numeric vector, and the only thing that would catch a mis-ordered grid is `build_recipe()`'s own monotonic check (`utils-recipes.R:47–63`), which aborts mid-`evaluate()` instead of at construction.

- **`R/class-core.R:271–445`** — three spec invariants remain unenforced, and the new verb widens the blast radius of each: (1) **role vocabulary** is never checked against `{id, predictor, covariate, outcome, meta}` — a typo'd role silently makes a column invisible to every consumer, which is now a live risk since `select_training()` appends role rows by hand at line 437–439; (2) **outcome cardinality** (I3, "at most one column has role `outcome`") is checked for `id` (line 408) but not for `outcome`; (3) the stored counts `n_rows`/`n_predictors`/`n_covariates`/`n_responses` are never compared against `analysis`/`role_map`. The contract says derived counts are computed, not stored (01-object-contract.md, "Computed Properties"); the implementation stores them, and `set_analysis()` is now the only thing keeping them honest. Since `standardize()` (`pipeline-standardize.R:737–739`) and `add_response()` (`pipeline-add-response.R:475–476`) still assign counts by hand, a three-line assertion in the validator is cheap insurance.

- **Contract vs. implementation: `x$selection` and the `response` role.** `x$selection` is a ninth top-level section. It is authorized by `select-training-design.md` ("On the object, `x$selection`"), but `01-object-contract.md` still documents exactly eight sections, and nothing validates the record's shape. That matters because `print.horizons_data` (`class-core.R:1666–1685`) dereferences six fields of it unguarded (`settings$scope`, `settings$k`, `pool_sizes$property/drawn/available`, `pool$n_rows`, `groups`, `exclusions`) — a partially-formed or hand-edited record turns `print()` into an error. Same class of drift: `role == "response"` and `data$n_responses` are load-bearing throughout the implementation but are not in the contract's role list (I3) or its Section 1 sketch. Update `01-object-contract.md` for both, and add shape checks for `$selection` to `validate_horizons_data()` (or a small `validate_horizons_selection()` called from the verb).

- **`R/pipeline-average.R:193,349–354`** — promoting the `by` column to `sample_id` does no type coercion. `group_values <- analysis[[by]]` takes the column as-is, and lines 349–354 just rename it. I2 says `sample_id` is character; a numeric or factor `by` column produces a non-character id that the validator will not catch (it only checks presence and uniqueness, lines 311–325). A factor id is the sharp edge: `dplyr` joins between a factor `sample_id` and the character `sample_id` in `models$row_index` / `ensemble$predictions` error out or coerce unpredictably. Coerce with `as.character()` at line 349 and assert no `NA` (the `anyNA(group_values)` guard at line 195 covers NA today, but the assertion belongs with the id promotion).

- **`R/pipeline-average.R:332`** — `col_order <- c(by, retained_meta, predictor_cols)` omits `response` and `outcome` columns, so `average()` called after `add_response()` drops them from `averaged` while `new_role_map` still lists them. Previously this produced a malformed object that `validate_horizons_data()` would flag later; now `set_analysis()` aborts immediately (`utils-subset.R:51–59`) with "Roles without a column: <response>", which blames the role map rather than telling the user that `average()` must precede `add_response()`. Strictly better than before, but worth either carrying response columns through the group collapse or aborting up front with the real reason. Same mechanism makes `average(by = "filename")` abort, since `filename` is force-dropped at line 320.

- **`R/class-core.R:1838–2308`** — `summary.horizons_data()` has no Selection section. `print()` gained one (line 1666), and summary is documented as "significantly more detail than `print()`", so an object drawn by `select_training()` shows less under `summary()` than under `print()`. The Pipeline Status block (line 2270–2294) is also unaware of selection state. Mirror the print block, at minimum the pool size, properties drawn, groups and twin count.

### Suggestions

- **`R/pipeline-select-training.R:655`** — `ps$available` is missing its `[i]` subscript in the `scope == "global"` branch (compare line 658, which has it). With more than one property `paste0` vectorizes and `cat` prints one garbled line per property.
- **`R/pipeline-select-training.R:436–439`** — no guard against `.drawn_by` / `.min_distance` / `.group` already existing on the pool. Running `select_training()` on a pool that is itself a prior selection triggers `bind_cols` name repair, then a confusing `set_analysis()` abort. An explicit check with a clear message costs two lines.
- **`R/pipeline-select-training.R:604` (`check_resemblance`)** — `sample.int(n, 2000L)` is unseeded and advances the caller's RNG. `cluster_targets()` goes to some trouble to save and restore `.Random.seed` (`select-neighbours.R:325–330`); this one does not, so the resemblance threshold and the "targets beyond the pool's spread" warning are not reproducible across runs, and the record in `selection$resemblance` can't be re-derived. ## spectroscopy

### Critical (silent — plausible spectra/predictions, wrong result)

- **`R/select-reconcile.R:128-148` and `:179` — coverage is checked on range endpoints only, so a gapped pool is spline-filled across the gap (R3b, R4c).** The two stops compare `target_grid$range` against `pool_grid$range`, i.e. `min`/`max` only. `standardize(remove_water = TRUE)` is a supported, documented path that *deletes columns*, leaving a pool with holes at 1580–1720 and 3100–3700 cm⁻¹. Such a pool passes both coverage checks, and `resample_spectra()` then runs `prospectr::resample(interpol = "spline")` over a `wav` vector containing a 140 cm⁻¹ and a 600 cm⁻¹ hole, evaluating the interpolant at target wavenumbers that lie inside the holes. Every pool row acquires invented absorbance across the OH bending and stretching regions, and those invented columns go into the returned training set as real predictors. It is silent because the output is smooth, finite, monotonic in index, passes `validate_horizons_data()`, and `grid_summary()` reports `resolution = median(abs(diff(sort(wn))))`, which a two-band gap barely moves — the record will say "resampled 4 → 8 cm⁻¹" and nothing else. `standardize()` itself knows this hazard (`R/pipeline-standardize.R:636-637`, 675: "Water bands last — resampling would fill gaps if done before"); `reconcile_axes()` reintroduces exactly the ordering `standardize()` was written to avoid. **Fix:** check grid contiguity/regularity, not just endpoints — reject (or segment) a pool or target axis whose spacing has outliers relative to its median, and record the gap in `record$pool_grid`. At minimum, refuse to resample across any interval wider than, say, 3× the median spacing.

- **`R/select-space.R:67-73` — the Savitzky-Golay derivative is run across whatever discontinuities the reconciled axis carries (R3b).** `prospectr::savitzkyGolay()` convolves over adjacent *columns*, with no knowledge of `wn`. If the targets were standardized with `remove_water = TRUE`, the reconciled grid is the targets' grid, so pool and targets alike are differentiated straight across the band edges: an 11-point window straddling a 1580→1720 jump differences 140 cm⁻¹ of unrelated absorbance and produces a large spurious feature at every gap edge, in both pool and targets. The edge-trim bookkeeping `wn <- wn[(h + 1L):(length(wn) - h)]` stays arithmetically correct, so nothing errors, names stay aligned, and the spikes enter the PCA as a high-variance direction that will dominate the leading components — neighbours then get chosen by "same water-band artefact," not "similar soil." The `mask` lever cannot repair this: masking happens *after* the derivative (correctly, per the spec) and so cannot undo a gap that was already present in the input axis. **Fix:** same contiguity guard as above, applied before `transform_similarity()`; the guard belongs on the axis, not on the mask.

- **`R/select-neighbours.R:55-67` with `R/select-space.R:216` — Mahalanobis whitening of variance-selected components makes the default metric noise-dominated and unstable to trivial pool changes. This is the design-level cause of the neighbour-overlap result.** Components are retained by cumulative variance (`ncomp = 0.99`, capped at 100), then `sweep(S, 2, sdev, "/")` gives every retained component unit variance in the distance. On SNV + first-derivative spectra the variance tail is detector and spline-ringing noise, so on a real library the 0.99 rule runs to the 100 cap and the trailing components have `sdev` one to three orders below PC1 — after whitening they carry the same weight as the dominant chemical axes. Two consequences, both silent: the ranking is largely noise, and `sdev` and the trailing *eigenvectors* are themselves unstable, because near-degenerate eigenvalues in the tail leave the subspace free to rotate under small changes in the row set. Since `sdev` enters as a divisor, its perturbation is amplified. I checked the mechanism on a synthetic 400 × 851 pool through the package's own chain: even at a mild 19 retained components and an 8:1 sdev ratio, components 11–19 take **47 % of the squared Mahalanobis budget against 6 % of the Euclidean**, and dropping 1 % of rows moves the top-40 neighbour sets by **2.2 % under Mahalanobis against 0.1 % under Euclidean** — a ~20× sensitivity gap at a sdev ratio of 8. At the 100-component cap with real ratios this scales to exactly the 0.94 overlap you saw after removing 165 of 45,856 rows. Nothing about the result looks wrong; the space is valid and the distances are finite. **Fix:** stop selecting components by cumulative variance alone. Add a noise floor (drop components whose `sdev` falls below a fraction of PC1, or use an eigenvalue-gap / broken-stick rule), and/or shrink the whitening (regularized Mahalanobis). Given `metric` is a lever the experiments are meant to settle, I would also record `variance_retained` *and* the sdev decay in `x$selection$settings` so a run's stability is auditable after the fact. This affects `find_twins()`, `check_resemblance()` and the recorded AD signal too — they all ride the same distances.

  (Coordinator note, measured on a 20,000-row KSSL sample at 4 cm⁻¹ with the water mask: the 0.99 rule retained 33 components, not the 100 cap; sd/PC1 for PC33 is 0.038, so the amplification is 26×. A floor at 0.10 of PC1 sd keeps 13 components; 0.05 keeps 27.)

- **`R/pipeline-select-training.R:454`, `R/select-space.R:65` — nothing checks that pool and targets are in the same photometric unit, and SNV makes the resemblance check structurally blind to the commonest mismatch (R6a).** The verb's only guard against a batch "in the wrong units or the wrong mode" is `check_resemblance()`, which measures in the similarity space — and that space begins with row-wise SNV, which removes per-spectrum offset and scale exactly. A pool in fractional reflectance-derived absorbance against targets in percent, or any pure gain/offset difference between instruments, produces **identical** similarity-space scores and therefore no warning at all, while the returned training set is in the pool's units and the model is later asked to predict targets in different ones. The docs promise this check catches units (`R/pipeline-select-training.R:494`); it cannot. **Fix:** compare the raw (pre-SNV) magnitude distributions of pool and targets — median absorbance, interquartile range, and sign — and warn on a gross mismatch, before the similarity space erases it.

### Important

- **`R/select-space.R:39-44`, `R/pipeline-select-training.R:84-86` — the SG window is in points, and the grid is now the *user's* grid, so `window = 11` is a different physical filter in every batch (R2c).** The default was calibrated at 2 cm⁻¹ (22 cm⁻¹ of bandwidth, `EXP_LOCAL`); a user who standardized to 8 cm⁻¹ gets an 88 cm⁻¹ window over the same default argument, and the pool is resampled to match so nothing errors. Since the targets' grid is the reference by design, the similarity space's effective smoothing is now coupled to a choice made two verbs earlier. The k = 400 default and every experimental result inherited from the 2 cm⁻¹ runs quietly change meaning. **Fix:** report the window in cm⁻¹ in the verbose chain line and in `settings` (`window × target resolution`), and consider accepting `window` in cm⁻¹ and converting to an odd point count against the reconciled grid.

- **`R/select-neighbours.R:131-145` and `:233-246` — the twin rule cannot catch replicate scans, which is the case it was written for.** `find_twins()` compares only `d1` to `d2`, and `draw_neighbours()` drops only `twins$pool_id[...][1]` — a single row. A KSSL sample present in the pool as two or three replicate scans gives `d1 ≈ d2 ≈ 0`, so the gap rule never fires (`d1 < 0.05 * d2` is false when both are ~0), and the only escape is the `d1 == 0` branch, which drops exactly one of the replicates and leaves the others in the neighbourhood at ~zero distance. Worse, `d1 == 0` is itself unreliable: the distance is computed by the cancellation-prone identity at `:92`, so a true duplicate frequently returns ~1e-8 rather than an exact 0. Net effect: a lab whose archive is the pool gets its own samples back in the training set and every downstream number is the lie the section was written to prevent. It is silent because the report prints "Twins excluded: 8" and looks like it worked. **Fix:** after the gap test, also exclude every neighbour within a small absolute multiple of `d1` when `d1` is itself near zero (a replicate cluster, not a single twin), and report the count per target.

- **`R/select-neighbours.R:92` — the `|a-b|² = |a|² + |b|² - 2a·b` identity loses all precision at small distances, which is where this code makes its decisions.** For near-identical score vectors the subtraction cancels, leaving a relative error around `sqrt(eps) · |a|`; `pmax(..., 0)` hides the negative results rather than flagging them. Twin detection, `check_resemblance()`'s assumption that column 1 is the self at distance 0, and the ordering of the closest few neighbours all live in precisely the regime the identity handles worst. Tests pass because `expect_equal()` on brute force carries a 1e-8 tolerance. **Fix:** keep the identity for the bulk screen, then recompute the retained k (plus the twin candidates) by direct differencing.

- **`R/pipeline-select-training.R:609-615` — `check_resemblance()` draws `sample.int(n, 2000L)` with no seed, so the applicability warning is not reproducible.** Two identical `select_training()` calls can name different targets as beyond the pool's spread, and the call silently advances the caller's RNG stream. The verb already takes a `seed` argument, and `cluster_targets()` carefully saves and restores `.Random.seed`; this path does neither. Reproducibility is part of correctness here — the threshold is the number a user would cite when defending a prediction.

- **`R/pipeline-select-training.R:358-370` — under `space_rows = "measured"`, distances in `target_distances`, `membership` and `.min_distance` come from different PCA spaces per property and are pooled into one column with nothing marking which space produced them.** Different rotations, different component counts (`ncomp_by_property` records this), different `sdev` — so the numbers are not on a common scale, while `resemblance$threshold` is computed once in the all-rows space and will be compared against them by anyone reading the record. **Fix:** carry a `space` column on the distance tables, or at least document in the return contract that the distances are within-property only.

- **`R/pipeline-select-training.R:262-265` — the *model's* pool spectra are point-sampled onto a coarser grid with no anti-alias smoothing.** `prospectr::resample(interpol = "spline")` evaluates the interpolant at the new wavenumbers; going 2 → 8 cm⁻¹ (the normal case, per the spec) is decimation by 4, which aliases narrow features and shifts apparent band positions rather than integrating them. `standardize()` has always done this, but here it is applied to an entire reference library whose value is precisely its fine detail, and it lands in the predictors the model trains on, not just the similarity space. Worth at least a documented caveat; smoothing to the target bandwidth before decimating would be the physically correct version.

- **`R/select-space.R:54-55` — the `mask` roxygen example is `rbind(c(1580, 1720), c(3100, 3700))`, which masks out the clay-OH structural stretch (R4d).** 3100–3700 overlaps the kaolinite/illite OH stretch at ~3620–3700, diagnostic for the clay content this package names as its first target — and the fixture's own second spectral family is centred at 3620. A user copying the example removes the strongest texture-diagnostic region from the space that chooses their texture-model neighbours. The default of `mask = NULL` is right; the example should not silently recommend the thing `standardize()`'s own default declines to do. Use a neutral illustrative range, or say what the water ranges cost.

### Suggestions

- `R/select-space.R:69` — no validation that `window` is odd, `poly < window`, or `poly >= derivative`; the code relies on `prospectr` to raise, while `h <- (window - 1L) %/% 2L` at `:70` already assumes odd. A local check with the package's own error class would fail more legibly (R2a).
- `R/select-neighbours.R:69-74` — cosine normalizes mean-centred PCA scores, so it is the angle about the *pool centroid*, not the spectral angle a chemometrician expects, and it is undefined for a target sitting at the centroid (`rowSums(S^2) = 0` → `NaN`, silently propagating into `order()`). Guard the zero norm and say in the docs what the angle is measured about.
- `R/select-reconcile.R:130-148` — the coverage test is exact, so a target grid overshooting the pool by a fraction of one spacing hard-stops the verb. A tolerance of half the pool's median spacing, with a clamp rather than an abort, is physically sound (no extrapolation beyond a half-step) and much kinder; the current message also does not say by how much the targets overshoot.
- `R/select-space.R:212` — `prcomp()` computes the full decomposition; at 45,000 rows the scores matrix alone is hundreds of MB and memory is the stated constraint. `rank. = max_comp` (or `irlba`) would cut it substantially.
- `R/select-space.R:84` — `apply(is.finite(m), 1, all)` materializes a full logical matrix plus `apply`'s row list; `rowSums(!is.finite(m)) > 0` is the same test at a fraction of the cost.
- `R/select-space.R:75-81` — no check that the mask leaves any columns; masking everything reaches `prcomp()` with a zero-column matrix and an opaque error.
- `R/select-neighbours.R:348` — `cluster_targets()` uses plain `dist()` on unscaled scores while the draw may use whitened Mahalanobis, so a cluster is not a neighbourhood in the same geometry. Defensible, but it should be a stated choice rather than an accident of two functions.

### Domain verified

- Transform order is correct throughout: SNV before the derivative, mask strictly after (`select-space.R:65-82`), and the mask is expressed in wavenumbers so it survives regridding onto the targets' axis. No column deletion precedes a window operation anywhere in the new code (R3a).
- SNV is row-wise and stateless via `prospectr::standardNormalVariate()` on the full matrix — correct axis, no stored parameter, no cross-sample leakage (R1a/R1b).
- The derivative's axis direction is consistent. `prospectr::savitzkyGolay()` differentiates along column index, so a decreasing wavenumber axis flips the sign globally; pool and targets pass through the same call on the same reconciled axis, and the global sign is immaterial to centred PCA distances. The edge trim `wn[(h+1):(length(wn)-h)]` matches `prospectr`'s `(w-1)/2` loss per end exactly (R2d). `poly = 2` with `derivative = 1` is fine (parity-identical to `p = 1`, not a defect).
- Targets are projected, never refitted: `project_similarity()` uses the pool's stored `center` and `rotation` (`select-space.R:299`), and refuses outright if the axes do not match, with `reconcile_axes()` named in the message. The PLS branch projects through the stored fit the same way (R1c-style discipline).

Every gap, unit, replicate, window-bandwidth and whitening-instability failure above requires a fixture the suite does not have.

## recipe-steps

Verified the recipes/hardhat semantics empirically against the installed versions (recipes 1.3.3, hardhat 1.4.3) rather than from memory; the repros are described inline.

### The change itself — correct

`R/utils-recipes.R:79-87`. `bake = FALSE` is the right requirement for a training-only, non-predictor role. Mechanism, confirmed: `hardhat:::get_extra_role_columns_original()` builds `blueprint$extra_role_ptypes` from `recipes:::compute_bake_role_requirements()` filtered to `TRUE`, and `forge_recipe_default_clean_extras()` `shrink()`s `new_data` to those ptypes — so with `bake = TRUE` a missing `.drawn_by` aborts inside `predict()` before any step runs. A minimal repro (recipe with an `id` role at `bake = TRUE` and a `meta` role, workflow fit, predict on new data lacking the meta column) errors under `TRUE` and passes under `FALSE`.

- When meta columns *are* present on new data, the workflow path no longer passes them to `bake()` at all — `extras$roles` excludes `meta`, so they are dropped before `recipes::bake()` is reached. A direct `recipes::bake(prepped, new_data)` still passes them through. So user-supplied meta from `spectra()` behaves correctly in the sense that nothing breaks and nothing currently consumes them, but the role is now training-only in the workflow path. If a future step ever needs a meta column at bake time (a group-aware transform, say), it will see it silently missing instead of erroring.
